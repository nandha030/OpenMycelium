WHY
---
0.3.0a10 cannot be reproduced from the commit it names.

It was built from a working tree where 42 shipped modules carried CRLF and the
rest carried LF. `.gitattributes` declares no rule for `.py`, so the checked-out
bytes depend on `core.autocrlf` -- true for the Windows git on this machine,
unset for the WSL git -- and the build ran across a mixture of the two.

Every one of those files was byte-for-byte the committed program. There were
ZERO content differences. The defect is reproducibility, not behaviour: no
single checkout produces that mixture, so the installed-content digest above
names a tree that cannot be recreated, and the entire identity model rests on
that digest naming the committed source.

Every gate passed on this build. That is the point. The program was identical,
so 443 unit tests, 220 installed-wheel tests, both scope reviews and the paired
hardware smoke all passed and nothing looked wrong. The defect surfaced only
because an unrelated `git reset --hard` normalised the working tree, after which
the installed-vs-checkout comparison began to fail.

THE TAG
-------
v0.3.0a10 remains on the remote and points at the Gate D.2 merge commit. It is
NOT deleted and NOT moved: tags are records, and moving one to hide a mistake
destroys the record. Deleting or moving it requires separate authorization.

Its message reads as a clean seal and does not mention any of this. Anyone
reading tags must read this file and docs/NONRELEASABLE_BUILDS.md alongside it.
