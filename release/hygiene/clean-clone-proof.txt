Clean-clone proof for *.py text eol=lf

The question: do the shipped Python bytes depend on the cloner core.autocrlf?
Both arms of each run clone the same ref, one with autocrlf=true and one with
false, and hash the shipped .py as checked out. Only the two arms of a run are
comparable; the value is not installedContentSha256, which hashes wheel entry
names instead of checkout paths.

  == the shipped Python does not depend on core.autocrlf ==

  Still outstanding, and not what this rule set out to fix:
  179 non-Python text file(s) differ from the index in the
  autocrlf=true clone -- .c, .sh, .js, .html, .css, .md and friends.
  installedContentSha256 covers .py only, so the artifact identity is
  now cloner-independent; but the dirty-tree guard refuses to build
  such a clone at all, so a default Windows clone cannot produce a
  releasable wheel until those types are declared too.
